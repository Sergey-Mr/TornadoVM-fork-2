## System Overview

The TornadoVM MCP Server is an AI-powered optimization service that takes GPU kernels (OpenCL or PTX) generated by TornadoVM and returns optimized versions using a multi-step LLM reasoning pipeline augmented with Retrieval-Augmented Generation (RAG).

### Core Philosophy

The server follows a **chain-of-thought optimisation approach**: rather than asking the LLM to optimize a kernel in a single prompt, the system decomposes the task into discrete reasoning steps — analysis, reference review, planning, and generation — maintaining conversational context throughout. This mirrors how a human GPU optimization expert would approach the problem: first understand the kernel, then study similar cases, then plan, then implement.

### Technology Stack

| Component | Technology | Purpose |
|-----------|-----------|---------|
| LLM | Claude Opus 4.6 (Anthropic) | Kernel analysis and code generation |
| Vector DB | Pinecone | Semantic search for similar optimizations |
| Embeddings | Voyage AI (`voyage-code-3`) | Code-specialized embeddings |
| Storage | Supabase (PostgreSQL) | Large PTX kernel storage |
| Observability | Langfuse | LLM call tracing and cost tracking |
| Framework | FastMCP + ThreadingHTTPServer | Dual protocol support (MCP + HTTP) |

## LLM Model Selection: Why Claude Opus 4.6

### The Model Selection Problem

Optimising GPU kernels requires an LLM that excels at:

1. **Low-level code generation** — Writing correct OpenCL/PTX with precise pointer arithmetic, index calculations, and memory barrier placement
2. **Extended reasoning** — Working through complex index calculations before committing to code (e.g., verifying that a tiled matrix multiplication correctly handles boundary conditions)
3. **Constraint adherence** — Following strict rules (TornadoVM's +4 array offset, signature preservation, grid-stride incompatibility with tiling) without drift across a multi-turn conversation
4. **Domain knowledge** — Understanding GPU architecture concepts: warps, occupancy, memory coalescing, bank conflicts

### Models Evaluated

During development, multiple LLM models were evaluated for kernel optimisation quality:

| Model | Provider | Strengths | Weaknesses for This Task |
|-------|----------|-----------|-------------------------|
| **Claude Opus 4.6** | Anthropic | State-of-the-art code generation, extended thinking, strong constraint following | Higher cost per call |
| Claude Sonnet 4.6 | Anthropic | Faster, cheaper | Less reliable on complex index calculations, more prone to constraint drift |
| GPT-4o | OpenAI | Good general coding, fast | Weaker on low-level GPU code, no extended thinking equivalent, less precise on TornadoVM-specific constraints |
| GPT-4-Turbo | OpenAI | Large context window | Same GPU code limitations as GPT-4o |
| GPT-o1 / o3 | OpenAI | Chain-of-thought reasoning | Slower, less controllable reasoning process, limited availability |

### Why Claude Opus 4.6 Was Chosen

**Claude Opus 4.6** was selected as the production model for several reasons:

1. **Best-in-class code generation**: At the time of development (early 2026), Claude Opus 4.6 was consistently the top-performing model on code generation benchmarks (SWE-bench, HumanEval, MBPP). For GPU kernel code specifically, it produced fewer compilation errors and more numerically-correct results than alternatives.

2. **Extended Thinking**: Anthropic's Extended Thinking feature gives the model a private "scratchpad" for working through complex calculations before outputting code. This is critical for kernel optimisation — the model can verify that tile indices, barrier placement, and boundary conditions are correct before committing to output. No other provider offered an equivalent feature with this level of control.

3. **Strong instruction following**: Across multi-turn conversations (Steps 1-4 accumulate 4+ turns), Claude Opus maintained adherence to the system prompt constraints (signature preservation, +4 offset, grid-stride rules) without drift. Other models tended to "forget" constraints by Step 4.

4. **Adaptive thinking budget**: Claude's thinking mode is adaptive — the model decides how much thinking it needs for each problem. A simple element-wise kernel gets minimal thinking; a complex tiled matrix multiplication gets extensive verification. This avoids wasting tokens on simple cases.

### Trade-Off: Quality vs. Cost

The choice of Opus 4.6 over cheaper models (Sonnet, GPT-4o) is a deliberate trade-off: **a failed optimisation costs more than an expensive successful one.** Each failed attempt triggers the feedback loop (additional LLM calls), wastes GPU benchmark time, and delays the experiment. Using the most capable model minimises failure rate, reducing overall cost despite the higher per-call price.

## TornadoVM Kernel Caching: Why Optimisation Is a One-Time Cost

### The Key Insight

Despite the ~$1 per-optimisation cost, the AI optimisation needs to be performed **only once per kernel**. TornadoVM's architecture includes a kernel caching mechanism that stores compiled kernel binaries, meaning the optimised kernel is reused on all subsequent executions.

### How TornadoVM Caches Kernels

TornadoVM uses a **multi-level caching system**:

**Level 1: In-Memory Code Cache (Default)**

Every TornadoVM device context maintains a `ConcurrentHashMap<String, InstalledCode>` that caches compiled kernels during a JVM session:

```java
// OCLCodeCache.java
private final ConcurrentHashMap<String, OCLInstalledCode> cache;

// On execution:
if (deviceContext.isCached(executionPlanId, taskId, methodName)) {
    return deviceContext.getInstalledCode(...);  // Return cached kernel
}
// Otherwise: compile from source and cache
```

Within a single JVM session, a kernel is compiled exactly once. All subsequent executions use the cached binary.

**Level 2: Optional Persistent Disk Cache**

TornadoVM supports persisting compiled kernel binaries to disk:

```bash
# Enable persistent caching
-Dtornado.opencl.codecache.enable=true
-Dtornado.opencl.codecache.dump=true
-Dtornado.opencl.codecache.dir=/var/opencl-codecache
```

Compiled binaries are written per device (e.g., `device-0-0/matrixMultiplication`), and can be reloaded on subsequent JVM restarts using the precompiled binary mechanism:

```bash
-Dtornado.precompiled.binary=path/to/binary,task.device=0:1
```

### Conversation Context Accumulation

The key design decision is that all steps share a single `Conversation` object:

```python
conversation = Conversation()

# Step 1: LLM analyses the kernel
conversation.add_user(analysis_prompt)
response1 = client.chat(conversation, SYSTEM_PROMPT)
conversation.add_assistant(response1.content)

# Step 2: LLM reviews RAG example (has Step 1 context)
conversation.add_user(reference_prompt)  # includes RAG example
response2 = client.chat(conversation, SYSTEM_PROMPT)
conversation.add_assistant(response2.content)

# Step 3: LLM plans optimisations (has Steps 1-2 context)
conversation.add_user(planning_prompt)
response3 = client.chat(conversation, SYSTEM_PROMPT)
conversation.add_assistant(response3.content)

# Step 4: LLM generates code (has Steps 1-3 context)
# Uses extended thinking for verification
conversation.add_user(generation_prompt)
response4 = client.chat_with_thinking(conversation, SYSTEM_PROMPT)
```

This means Step 4 can reference its own earlier analysis. For example, if Step 1 identified "memory-bound with strided access", Step 4 can use local memory tiling to address that specific finding.

### System Prompt: The Constraint Backbone

The system prompt (`prompts/system.py`) is included in **every** LLM call across all steps. It encodes the non-negotiable constraints of TornadoVM kernel optimisation. These constraints are listed in **priority order** — the first rule takes precedence in case of conflict:

1. **Function signature MUST be identical** to the original kernel — same name, same parameters, same types, same order
2. **Numeric precision MUST be preserved** — NEVER convert FP64 to FP32, NEVER replace `double` operations with `float` equivalents, NEVER use approximate math functions (`native_rsqrt`, `half_rsqrt`) that reduce precision
3. **Dimension source MUST be preserved** — if the original reads N from `_kernel_context[0]`, the optimised kernel must do the same
4. **Arrays need +4 offset** for float data (TornadoVM's 16-byte array header)
5. **No hardcoded sizes** — use the kernel's dimension source, not new literals
6. **`global_work_size`** uses parameter NAMES (resolved at runtime), **`local_work_size`** uses concrete integers
7. **`local_work_size` MUST match tile dimensions** when tiling is used
8. **Work-group sizes must not exceed device limits**
9. **Use `//` comments in OpenCL** (single `/` causes compilation failure)

#### The Precision Preservation Rule

Rule 2 deserves special attention. TornadoVM compiles Java code to GPU kernels and **preserves Java's numeric semantics**. If the Java source uses `double`, the generated kernel uses `double`. An LLM that silently converts `double` to `float` would:

- **Violate the correctness contract** — the optimised kernel would produce different numerical results than the Java code
- **Inflate speedup numbers** — on consumer NVIDIA GPUs (RTX 4090: 82.6 TFLOP/s FP32 vs 1.29 TFLOP/s FP64, a 64x throughput ratio), FP64→FP32 conversion alone can produce 5-60x speedup that has nothing to do with structural optimisation
- **Create false benchmarks** — reporting "15x faster" when the real change is "we used less precision" is misleading

During early experiments (before this rule was added to the system prompt), the LLM applied FP64→FP32 conversion to NBody (`rsqrt(double)` → `native_rsqrt(float)`, 6.6x speedup) and MonteCarlo (15.2x speedup). While these are valid transformations when the user explicitly requests reduced precision, they must not be applied automatically by an optimisation system.

The system prompt now explicitly forbids this:

```
⚠️ CRITICAL: NEVER Change Numeric Precision ⚠️

- NEVER convert double (FP64) to float (FP32)
- NEVER replace rsqrt(double) with rsqrt(float) or native_rsqrt(float)
- NEVER remove double↔float casts that exist in the original kernel
- NEVER replace sqrt, rsqrt, exp, log with approximate/native variants
  that reduce precision

Only the user may decide to reduce precision — the optimisation system
must never do this automatically.
```

### Why Pinecone?

1. **Managed service** — No infrastructure to maintain during a research project with limited time
2. **Namespace support** — Clean separation between OpenCL and PTX kernel collections
3. **Metadata filtering** — Can filter by device family at query time
4. **Sub-100ms queries** — Fast enough for real-time use in the optimisation pipeline
5. **Free tier** — Sufficient for research-scale data (hundreds of kernels, not millions)

## Embedding Model (Voyage AI)

### Why `voyage-code-3`?

1. **Code-specialized** — Unlike general-purpose embeddings (e.g., OpenAI `text-embedding-3`), Voyage's `voyage-code-3` was trained specifically on source code. It understands code structure (loops, conditionals, function signatures), programming patterns (reduction, tiling, SIMD), and language-specific idioms (`__local`, `.shared`).

2. **Semantic code similarity** — Two kernels implementing the same algorithm with different variable names or slightly different structure will have high cosine similarity. A general-purpose embedding model treats code as text and might miss the computational equivalence.

3. **Cross-pattern understanding** — Can match an OpenCL kernel using `float4` vectorisation to a similar kernel without it, because it understands the underlying computation is the same.

4. **Benchmark performance** — Voyage AI's code embeddings consistently rank at the top of code retrieval benchmarks (MTEB Code Retrieval).

### Embedding Dimension

`voyage-code-3` produces **1024-dimensional vectors**.

## Supabase Integration

### Why Supabase?

PTX kernels are significantly larger than OpenCL kernels. A typical OpenCL kernel is 1-5 KB; PTX (being a low-level assembly-like IR with explicit register declarations) can be 10-50 KB. Pinecone has metadata size limits (~40 KB) that make storing full PTX source directly impractical, especially when both original AND optimised kernels need to be stored.

**Solution:** Store PTX kernel source code in Supabase (PostgreSQL) and store only a reference ID in Pinecone metadata.

### Hybrid Storage Flow

```
POPULATING:
  PTX kernel pair ──> Supabase table (full source) ──> returns row UUID
  Original kernel ──> Voyage AI ──> embedding vector
  Vector + metadata (supabase_id=UUID) ──> Pinecone "ptx" namespace

QUERYING:
  Input kernel ──> Voyage AI ──> embedding
  Embedding ──> Pinecone "ptx" ──> metadata with supabase_id
  supabase_id ──> Supabase ──> full PTX source (original + optimised)
  Full example ──> Step 2 of pipeline
```

### Feedback Prompt Design

The feedback prompts are carefully designed for each failure category:

**For compilation errors:**
```
The previous optimisation attempt FAILED TO COMPILE.
Error: [raw error message]
AI Diagnosis: [explanation, likely_cause, suggested_fix from /explain-error]

Analyse what went wrong. Common compilation issues:
- Changed the function signature (most common cause)
- Used undeclared variables
- Syntax errors (single / instead of // for comments)
- Work-group size exceeds device limits
- Macro not defined
```

**For validation errors:**
```
The previous optimisation attempt PRODUCED WRONG RESULTS.
It compiled and ran, but the output does not match the sequential reference.

Analyse what went wrong. Common validation issues:
- Missing +4 array offset (TornadoVM header)
- Incorrect loop bounds (off-by-one)
- Missing barrier() between local memory writes and reads
- Changed function signature (parameter reordering)
- Grid-stride loop with wrong stride value
```

**For performance regression:**
```
The previous optimisation attempt was SLOWER than the original.
Original: [X] ms, Optimised: [Y] ms ([Z]% regression)

Analyse what went wrong. Common performance issues:
- Work-group size too small → poor GPU occupancy
- Grid size too small → not enough threads for the problem
- Local memory overhead exceeds benefit for this problem size
- Excessive barrier synchronisation
- Register spilling due to aggressive unrolling
```

## Observability (Langfuse)

### Why Langfuse?

1. **LLM-specific** — Built for tracking LLM calls (not generic HTTP requests)
2. **Token and cost tracking** — Tracks input/output/thinking tokens per call
3. **Trace visualisation** — See the full Steps 1-4 chain in a single trace view
4. **Session grouping** — Multiple optimisation attempts grouped under one session
5. **Prompt debugging** — Review exact prompts and responses for each step

### Tracing Structure

```
Langfuse Trace (one per /optimize call)
│
├── Metadata: backend, device_family, kernel_length, session_id, attempt_number
│
├── Span: "step1-analyze"
│   └── Generation: prompt → response (input_tokens, output_tokens)
│
├── Span: "step2-reference"
│   └── Generation: prompt → response
│
├── Span: "step3-plan"
│   └── Generation: prompt → response
│
├── Span: "step4-generate"
│   └── Generation: prompt → response + thinking_tokens
│
├── (If feedback:)
├── Span: "step5-feedback-analysis"
│   └── Generation: prompt → response
│
└── Span: "step6-feedback-generate"
    └── Generation: prompt → response + thinking_tokens
```

### File Logging

Local debug logs are stored in `logs/`:
```
logs/
├── mcp_opt_20260415_143022_abc123.log
└── ...
```

Each log captures: full prompts, full responses, RAG examples, extracted kernel code, and error messages.

## LLM Client Design

### Client Modes

| Mode | Method | Used In | Extended Thinking |
|------|--------|---------|-------------------|
| Single-shot | `generate()` | Error analysis | No |
| Multi-turn | `chat()` | Steps 1-3, feedback analysis | No |
| Multi-turn + thinking | `chat_with_thinking()` | Steps 4, 6, 8 (generation) | Yes (adaptive) |

```python

    # Thinking content is captured separately (chain_of_thought["step4_thinking"])
    # but NOT included in the conversation context
```

### Token Budget

| Step | Max Tokens | Thinking Budget | Purpose |
|------|-----------|----------------|---------|
| Step 1 (Analyse) | 1500 | None | Short analysis |
| Step 2 (Reference) | 1500 | None | Technique list |
| Step 3 (Plan) | 1500 | None | Strategy selection |
| Step 4 (Generate) | 4000 | ~10000 (adaptive) | Full kernel code |
| Step 5+ (Feedback) | 1500 | None | Failure analysis |
| Step 6+ (Retry) | 4000 | ~10000 (adaptive) | New kernel code |

## API Specification

### POST /optimize

Full optimization pipeline. See [Detailed MCP Server Internal Architecture](#detailed-mcp-server-internal-architecture) for the processing flow.

### POST /explain-error

Error diagnosis without optimization. Used to get structured error analysis before the feedback loop.

### GET /health, /devices, /backends, /modes

Service discovery endpoints.

### MCP STDIO Protocol

In addition to HTTP, the server implements the Model Context Protocol (STDIO) for integration with AI coding assistants and IDE extensions. This provides the same optimisation capabilities through a standardised tool interface.
